# OmniEng Reference Registry — V&V Diagnostic Ledger

> **Engineering audit artifact — NOT certification evidence.**
> This ledger documents the identity and provenance of every validation & verification (V&V) diagnostic wired into `test/vv/run_vv.js`, plus the unavailable-reference roster in `src/core/vv/validation_readiness.js`. It records what each case actually tests, the class of its reference, publisher/source/license where known, SHA-256 pins when the code carries them, whether a production solver executes, and the current outcome.
>
> "PASS" here means the diagnostic's own declared tolerance was met. It does **not** establish solver accuracy, standards compliance, certification, or release maturity. Several cases compare against analytic or manufactured substitutes rather than independent published data; those are labeled precisely below.

## 3. Separate core `VVRegistry` diagnostic API

`src/core/vv/vv_registry.js` is a separate experimental API, not the test runner in §1. Its descriptive diagnostic IDs are `NASA_TMR_CORRELATION_DIAGNOSTIC` (correlation integration only; no flow solver), `HERTZ_AXISYMMETRIC_CONTACT_DIAGNOSTIC` (axisymmetric discretization, not 3D contact FEA), `SPARSE_SPD_GENERATED_SUITE` (generated, not NIST), `CANTILEVER_BEAM_ANALYTIC_DIAGNOSTIC` (synthetic beam inputs, not Hannover data), and `OPTICAL_PSF_PARAXIAL_DIAGNOSTIC` (formula helpers, not ISO qualification). The named-reference IDs NAFEMS_LE1/LE10/LE11/FV32/T1, NASA_TMR_FLAT_PLATE, HERTZ_CONTACT_3D, NIST_SPARSE_ROBUSTNESS, HANOVER_BEAM_DYNAMIC_RESPONSE, and ISO_10110_OPTICS_TOLERANCE are not registered as executable substitutes in this separate API; `runVVBenchmark()` returns unavailable for those names there (the §1 runner is the executable path for the NAFEMS and NASA cases). All remaining core registry results carry experimental maturity, `validationReady: false`, and `releaseApproved: false`.

## 4. Audit note

- This registry is a **self-audit artifact**: it records what the diagnostics compare against and what is missing. It is not a certificate, a compliance statement, or a release sign-off.
- Where a reference class is `analytic` or `manufactured`, the case exercises the production solver but does not provide independent physical validation. The `MOOSE_*` cases are genuine cross-solver correlations against a named published source; the `NASA_TMR_FLAT_PLATE` case is the only bundled-external-data comparison, and it currently fails.
- `NASA_TMR_FLAT_PLATE` remains failing fail-closed after the numerical remediation; the benchmark does not use a canned result or relax its declared tolerance. Measured Cf deviation is ≈ 9.2% on a stationary run (improvement on the historical 28.3%), with 2026-11-01 re-measures also logging non-stationary and numerical-termination outcomes; the current per-run state is recorded in §1 and in the generated report.
- `NAFEMS_LE11` fails under the documented restraint set; the measured discrepancy is a stress-reporting-convention question at point A (nodal extrapolation vs element-averaged value) that the paywalled original booklet does not resolve (full audit trail in `test/vv/nafems/test_nafems_le11.js`).
